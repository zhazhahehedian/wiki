# 首次菜单加载优化验证

本地开发日志记录首次 `GET /hub/registry` 耗时 7838ms，同期 `/hub/[section]` 编译耗时 2.5s、2290 个模块；随后进入游乐场请求耗时 182ms。这是开发服务首次页面加载的证据，不是注册中心业务 API 的耗时测量。

原先七个菜单共用 `[section]/page.tsx`，该入口同时引用注册中心、游乐场、设置及治理页面。现在各菜单使用独立静态路径入口，URL 保持不变；新增 Hub 路由加载提示。注册中心数据请求保留自己的局部加载状态。

同一依赖环境下，生产构建报告的注册中心 First Load JS 从原共享入口约 286 kB 降至 129 kB。该指标包含共享脚本，不能直接换算为用户的等待时长。

验证：

- `pnpm build` 通过，包含 lint、类型检查；七个独立菜单路由均成功构建。
- Chromium 使用模拟 HTTP，在注册中心页面脚本被暂停下载时显示「正在加载页面」，侧栏保持可见；脚本就绪、目录 API 仍未响应时，显示注册中心页面与局部加载提示。
- 七个菜单客户端跳转正常，直接请求均返回 200；未知菜单路径返回 404；无浏览器运行错误。
- `browser-check.cjs` 可复现以上检查，截图及结果位于同目录。前端构建时 API base 与 `APP_URL` 一致，默认 `http://localhost:13003`；需可用的 Playwright 环境。

本地 Git 排除的启动脚本增加常用页面预热，在最终「服务已就绪」提示前访问首页、注册中心、我的发布、游乐场和设置；预热失败会明确提示，不会假报预热成功。Bash 语法与 ShellCheck 通过。脚本仍仅供本地使用；预热在下次启动时执行，开发服务后续重新编译或淘汰缓存仍可能产生等待。
