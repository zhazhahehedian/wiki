# Skill 生成等待、输出预算与失败诊断

2026-09-08，处理真实测试中长时间无明显反馈和「模型服务不可用」的问题。

## 现场证据

现有本地后端日志 `.cache/dev-local/backend.log` 记录：

- 00:06:02：`POST /api/v1/skill-builder/turn` 返回 502，耗时 9.781256539 秒，类别 `model_service_failed`。
- 00:08:15：同一路由返回 200，耗时 7.568622748 秒，对应成功的追问。
- 00:09:58：同一路由返回 502，耗时 46.24550256 秒，类别 `model_service_failed`，请求编号末尾 `000068`。
- 00:24:24 服务重启后，00:28:06 同一路由仍返回 504，响应体为空，耗时 60.000753173 秒。检查发现路由外层仍有全局 60 秒超时，覆盖了模型代理的新时限；对应用户后续截图中的 `Gateway Timeout`。
- 00:36:00 再次重启后，00:39:16 同一路由返回 `502 invalid_skill_generation`，耗时 76.405369907 秒，请求编号末尾 `000015`，说明本次已越过旧 60 秒限制。旧代码不读取长度上限结束原因，并丢弃 JSON/文件校验的具体原因，无法从这条历史日志断定是否截断。
- 00:57:29 服务重启后，00:59:11 和 00:59:30 返回 `502 model_upstream_rejected`，分别耗时 7.798304125 秒、5.545689979 秒，请求编号末尾为 `000010`、`000012`；01:01:43 同一路由成功返回 200，耗时 93.762411095 秒、响应 8909 字节。用户报告失败为自定义/带参考说明需求的上游 503，而一句话预设需求可成功。现有日志可确认两次失败是上游 HTTP 拒绝，发生在草案 JSON 校验之前；日志未保存上游状态/具体原因、模型、预算或输入，不能证明上下文超限、内容限制或线路故障。8909 是 HTTP 响应字节数，不是模型 token 用量，也尚未完成同一模型、预算和输入的对照复现。

旧模型代理的总时限为 45 秒，HTTP 客户端总时限为 50 秒，等待响应头为 15 秒。46.25 秒的失败与代理总时限高度吻合，很可能是复杂草案未生成完即被平台取消。旧日志没有保留细分原因，因此不能排除上游在该时刻断开；较早的 9.78 秒失败也不能据此认定是同一原因。

浏览器调用的是普通 JSON 接口，后端收集完整模型输出并校验后一次返回草案；等待中不显示逐字内容是当前接口行为。

生成时的滚动条频闪可在真实浏览器复现：短消息区的可视高度为 116px，旋转图标的变换范围让内容高度在 116px 和 117px 间变化，反复触发纵向溢出。

## 修复

- 共享模型代理总时限改为 5 分钟；响应头等待上限 60 秒；客户端兜底 6 分钟。模型列表发现保留 20 秒，连接/TLS、地址限制、密钥隔离、取消与输出限制保留。
- 两条模型生成 POST 路由的外层时限设为 6 分钟，为模型自身的 5 分钟时限和结构化错误留出余量；其他路由保留 60 秒，调用方取消仍向下传递。
- 超时返回 `504 model_response_timeout`，不完整流返回 `502 model_stream_interrupted`，上游 HTTP 拒绝返回 `502 model_upstream_rejected` 及安全状态码。格式/草案校验失败仍为 `invalid_skill_generation`；不回传上游原始诊断或密钥。
- 右侧草案区增加旋转图标、文档占位动画、真实等待秒数；等待 45 秒后说明复杂草案可能耗时较长。无虚构百分比或已完成阶段，支持减少动画偏好。
- 生成中的需求立即展示；修改期间保留原草案。失败保留输入与材料，显示请求编号以便对应日志。
- 修复浏览器中点击停止后按钮变为提交按钮、同一次点击误触发表单重新生成的问题；阻止停止点击的默认动作。
- 将消息区旋转图标放入固定尺寸并裁剪溢出的容器，保留动画，避免旋转范围改变滚动高度；长对话仍按实际内容滚动。
- 识别 OpenAI 兼容流的 `finish_reason=length` 与 Anthropic 流的 `stop_reason=max_tokens`，提示因输出上限截断；即使部分输出恰好可解析，也不当作完整草案返回。普通游乐场已输出文本时同样给出明确错误。
- 将草案错误细分为 `token_limit`、`empty_response`、`incomplete_json`、`invalid_json`、`invalid_response`、`invalid_draft`、`response_too_large`。保持 `invalid_skill_generation` API 错误码兼容，在提示及 details 中提供具体原因；日志仅记录原因码、字节数和请求编号。附件校验使用平台定义的提示，不记录或回传模型原文、未知字段名及原始解析错误。
- 用户随后明确以 Opus 5、Kimi K3、GPT-5.6 为主要使用范围：Skill 默认预算从 8192 提高为 65536，增加页面内的“生成设置”，可填写 1–1048576 的整数并传入 `max_tokens`。共享代理和游乐场参数输入同步扩大范围；模型仍决定实际支持能力。HTTP 400/422 拒绝提示检查输出长度、采样参数和模型名称；截断提示包含本次请求预算。无自动重试，保留独立的正文/附件/响应体积限制。
- 对外 OpenAI 兼容请求改用 `max_completion_tokens`，Anthropic 保留 `max_tokens`（未设置时默认 65536），不向上游同时发送两个预算字段。Skill 不再固定发送 `temperature=0.3`，避免 Opus 5 等模型拒绝非默认采样参数；已有思考增量过滤保留。
- 针对上述 503 补充诊断：只读取上游 `error.code` / `error.type` 中白名单内的机器错误码，按明确证据提示上下文超限、线路不可用、负载过高、限流、额度或参数/请求问题。无明确原因的 503 保留中性提示，不声称是 token 截断。错误体最多读取 16 KiB、等待 2 秒；未知值、消息正文及凭证不进入日志或页面。
- 生成成功及模型/草案错误增加安全元数据：请求编号、模型、对话条数、对话/素材/当前草案字节数、请求输出预算及耗时。可供下次失败与预设成功请求对照，但不存储用户内容，也不能补回旧请求的上游原因。本次没有把增加诊断当作已修复真实 503。

## 当前模型规格核对

2026-09-08 查阅官方文档：

- [Claude Opus 5](https://platform.claude.com/docs/en/models/opus-5/whats-new-opus-5)：128K 输出，默认开启思考，思考也计入 `max_tokens`。其[请求参数文档](https://platform.claude.com/docs/en/api/http/messages/create)明确不接受非默认温度。
- [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)：`gpt-5.6` 别名指向 Sol，最大输出 128000；[Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)使用 `max_completion_tokens`，包含可见输出与推理 token。
- [Kimi K3](https://www.kimi.com/help/kimi-api/api-troubleshooting)：默认 `max_completion_tokens=131072`，最大输出受 1M 上下文减去输入 token 约束；[请求参数](https://platform.kimi.com/docs/api/chat)允许设置到 1048576，但输入加预算超过模型上下文会被拒绝。

平台的 64K 是默认请求预算，1M 是参数校验边界，均不代表所有模型都能输出这么多。未对用户接入的中转服务做能力探测，也未据此认定上一条历史失败就是 token 截断。
