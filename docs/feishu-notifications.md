# 飞书消息通知：应用配置

对应实现：`backend/internal/notify`、`backend/internal/infra/feishu/bot.go`。默认关闭；开启前先在飞书开放平台完成以下配置。

## 1. 应用配置

在当前 Capability Hub 自建应用中：

1. **应用能力 → 机器人**：启用机器人能力。
2. **权限管理 → 应用身份权限**：开通 `im:message:send_as_bot`（以应用的身份发消息）。只需这一项，不需要读取消息、群组或通讯录的应用身份权限。
3. **版本管理与发布**：创建版本并发布，同时确认**可用范围**覆盖需要接收通知的人员（发布者、审核员、使用者）。可用范围以外的人员会收到飞书错误码 230013，平台不再重试，其他人照常发送。

## 2. 平台配置

在服务环境变量中设置 `FEISHU_NOTIFY_ENABLED=true` 并重启后端。依赖现有 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 与 `FRONTEND_ORIGIN`（消息中的链接）。启动日志不再出现 `Feishu notifications disabled` 即表示已开启。

## 3. 通知规则

| 事件 | 接收人 | 内容 |
|---|---|---|
| 提交审核 | 全部审核员与管理员 | 待审核，附审核链接 |
| 通过 / 强制上线 | 发布者 | 已上线 |
| 新版本上线 | 下载过旧版本、且仍有查看权限的人 | 版本更新，附市场链接 |
| 驳回 | 发布者 | 驳回原因 |
| 下线 | 发布者与全部历史下载者 | 已下线及原因 |

操作者本人不会收到自己操作的通知；可见范围调整与发布新草稿不发通知。

## 4. 可靠性

- 通知任务与状态变更、审计在同一数据库事务中写入 River 队列 `notify`：状态变更回滚则不会发通知，状态已提交则通知一定入队。
- 接收人在发送时解析：先生成一条事件任务，再按每位接收人拆成独立发送任务（最多 8 次重试）。每条消息带稳定的去重键，飞书会丢弃重试导致的重复消息。
- 发送失败只记录飞书数字错误码，不记录消息正文或令牌。

## 5. 验收

本功能目前只用模拟的飞书服务做过单元测试，还没有用真实应用和账号验收。开启后建议：普通账号提交 → 审核员收到；审核员驳回 / 通过 → 发布者收到；发布新版本 → 下载过的同事收到；下线 → 下载者收到；再把一名不在可用范围的同事加入名单，确认其他人仍正常收到。
