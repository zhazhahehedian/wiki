# MCP 程序包分发

2026-11-05 用户确认补齐 MCP 上传、下载；平台不提供运行托管。

## 行为与兼容

- 注册/编辑 MCP 可上传一个 ZIP 程序包；平台保存到现有对象存储，绑定精确版本。使用者在市场详情下载后按包内 README 安装、配置和运行。
- MCP 可以只有程序包，无须先部署服务。支持声明 `stdio` 或 `streamable-http`；stdio 不填写 Endpoint，鉴权为 none。HTTP 的 Endpoint 可选，但 Endpoint 和程序包至少具备一个。
- 已有仅 Endpoint 的远程 MCP 继续可用，也可附带程序包。平台不启动、执行或自动安装包内代码。
- 同一未发布版本未选择新文件时保留原包；新上传替换完整包。新版本不隐式继承旧包；只分发程序包时必须重新上传。已发布版本不可覆盖。
- 程序包上限 100 MiB，ZIP 内最多 2000 条目，解压后总量上限 500 MiB（2026-11-06 已调整，见文末「分片与断点续传」）。校验 ZIP 完整性、相对路径、重名/路径冲突；拒绝加密、符号链接和特殊文件。包内建议包含 README、启动命令、依赖说明和配置示例。平台不落盘解压、不提供 MCP 文件在线预览。

## API、权限和存储

- 复用 session 与发布 API 的 POST/PUT capabilities：multipart `metadata` + 单个 `files` ZIP。Skill 原有 50 文件 / 10 MiB 规则不变。
- 复用 `GET /capabilities/{slug}/versions/{id}/bundle`，包括 `/api/v1/open` 的 read scope。返回原始 ZIP，以附件形式下载；不公开 MinIO 地址或持久公开链接。
- 下载每次检查现有详情版本投影：Owner/Admin 可管理；独立审核员仅在待审状态获取允许审核的版本；普通使用者仅获取有权限的上线版本；发布凭证不继承审核员角色。下线、撤权和版本更新后按现有边界拒绝后续请求。
- 延用数据库的历史列 `skill_bundle_key` 作为通用版本包引用，API 仍只返回 `has_bundle`。新增 0021 迁移调整类型/传输约束，无须改 sqlc 查询。迁移保留现有 MCP/Skill 数据；若存在旧结构不能表达的 MCP 程序包或 stdio 版本，回退明确失败，不删除文件或版本。
- 对象键随机生成，写入失败不建版本；事务失败仅清理确认未引用的新对象，不清理提交结果不明的对象。

## 2026-11-05 补充：传输、校验、预览与通知

用户在公司电脑 review 后确认：业务上 MCP 包预计不超过 10 MiB，不做分片/断点续传；保留 100 MiB 硬上限。（2026-11-06 被下文取代：实际出现 150 MiB 的包。）

- 上传（multipart）与 bundle 下载使用 3 分钟请求超时，其余 API 保持 1 分钟。
- 单进程最多 4 个并发 multipart 保存，超出时排队，限制内存中同时缓冲的包。
- 使用方式：业务人员下载 ZIP 后直接交给 WorkBuddy、ChatGPT 等支持导入的客户端安装，平台不生成客户端配置，也不要求填写启动命令（曾考虑的启动说明字段已取消）。
- 迁移 0022：历史列 `skill_bundle_key` 更名为 `bundle_key`；新增 `bundle_sha256`、`bundle_size` 与 `bundle_findings`（上传时计算，旧包保持为空、不补算）。这些都是可由包推导的数据，0022 可正常回退；0021 原有拒绝规则不变。
- 上传扫描：校验 ZIP 时顺带检查 `.env`、私钥/证书、凭证配置文件、`.git` 目录，以及 1 MiB 以内文件中的私钥头、云 AccessKey、常见 API Token 格式（总扫描量 64 MiB、最多 50 条）。结果仅提示审核员和发布者，不阻止上传。
- 包内容预览：管理、审核与市场详情可查看 MCP 包的文件清单并直接阅读 README；256 KiB 以内的 UTF-8 文件内联（每次最多 4 MiB），服务端每进程最多同时读取 2 个包，不落盘解压。
- 下载统计：市场卡片与详情显示下载次数（来自下载审计）；发布者与管理员可查看按人汇总的下载记录（`GET /capabilities/{slug}/downloads`）。
- 飞书通知：见 [飞书消息通知](../../feishu-notifications.md)。通知事件与状态变更同事务写入 River。
- 下载响应使用 `{slug}-{version}.zip`，附带长度与 `X-Bundle-SHA256`；每次成功下载写审计 `download`，审计失败则不返回包。
- 服务每 6 小时（启动后 1 分钟首次）清理 `registry/` 下超过 24 小时且无版本引用的对象，逐个复查数据库引用；失败仅记录日志，下一轮重试。
- Skill 与 MCP ZIP 共用路径、重名与文件/目录冲突规则（`bundleTree`）。

## 验证计划

- ZIP 完整性、路径/体积/数量限制、取消、存储失败及安全清理。
- 隔离数据库迁移 up/down/up，已有数据保留与有新数据时拒绝有损回退。
- HTTP 上传/下载字节一致、CSRF/Owner/可见范围/审核员与发布凭证隔离；版本替换、发布后不可覆盖、新版本审核及下线。
- 前端注册/编辑验证、市场与管理下载入口、无 Endpoint 程序包展示；测试、类型检查、构建和页面检查。

## 2026-11-06 补充：分片与断点续传

实际已有 150 MiB 的 MCP 包，取代上文「不做分片」的决定。用户确认：上限 500 MiB；上传者都在公司内网；先做浏览器端，发布 API 保持单次请求。

- 上限：存储的 MCP 包 500 MiB；最多 20000 条目、解压后 2 GiB（带 `node_modules`、模型文件的包条目多）。单次 multipart 请求（发布 API，以及仍可用的旧表单路径）保持 100 MiB，因为它在内存中缓冲。Skill 规则不变。
- 浏览器流程（session + CSRF，仅上传者本人可见）：
  - `POST /api/v1/bundle-uploads` `{file_name, size}` → 创建上传，服务端在 MinIO 开 multipart upload，返回 `id`、`part_size`（8 MiB）、`part_count`。每人最多 5 个未完成上传（超出 429）。
  - `PUT /bundle-uploads/{id}/parts/{n}`：原始字节，长度必须恰为该分片大小；重传覆盖。服务端逐片转发到 MinIO，每进程最多同时缓冲 8 片（约 64 MiB）。
  - `GET /bundle-uploads/{id}`：返回 `received_parts`，客户端只补传缺失分片。
  - `POST /bundle-uploads/{id}/complete`：合并分片，流式计算 SHA-256，用 MinIO 范围读取（8 MiB 窗口）完成原有的 ZIP 校验与凭证扫描，不把整包读入内存、不落盘。幂等；合并后校验遇到存储故障可重试；包无效则删除对象并结束上传（400）。每进程最多同时校验 2 个包。
  - `DELETE /bundle-uploads/{id}`：取消。
  - 保存能力时在 metadata 里传 `bundle_upload_id`（仅 MCP，不能同时带 files），版本直接引用已上传对象并沿用其 SHA-256、大小、扫描结果；保存成功后上传记录删除，同一上传不能再被引用。保存失败保留上传，可直接重试。
- 续传：前端以「文件名 + 大小 + 修改时间」在 localStorage 记住上传 ID；暂停、断网或刷新页面后重新选择同一文件即从已收到的分片继续。分片失败按指数退避重试 5 次，客户端错误不重试。选择文件后立即开始上传，上传与校验完成前不能保存。
- 生命周期：上传 12 小时过期（低于孤儿包 24 小时门槛）。现有每 6 小时的清理任务先结束过期上传（未完成的 abort MinIO multipart），已合并但未保存的对象交由原孤儿清理按数据库引用复查后删除。迁移 0023 新增 `capability_bundle_uploads`，回退只丢失进行中的上传会话。
- 预览与下载：包内容预览改为范围读取（只读 ZIP 目录与小文件，单次最多拉取 64 MiB，超过后不再内联但清单完整）；bundle 下载超时从 3 分钟延长到 15 分钟，单个分片请求仍是 1 分钟，合并校验 3 分钟。
- 部署注意：浏览器每个请求最大约 8 MiB，前置代理需允许该请求体（nginx 默认 `client_max_body_size 1m` 不够），下载需允许 15 分钟。
