## 0. 背景与动机

阶段 2（确定性 RAG 闭环）已完成并本地验证，但实际使用中检索精度不足，症状覆盖整条链路：

1. 切片内容本身破碎（句子不完整、段落粘连）；
2. 命中完全不相关的切片；
3. 命中对的文档但错的段落；
4. 相关切片排名靠后；
5. 引用高亮范围过大，带出无关内容。

排查中已实锤两个内容损坏 bug：

- **Splitter 分隔符丢失**（已修复，2026-07-07）：`recursive_char.go` 用 `strings.Split` 切分后丢弃分隔符再拼接，中文文本丢失全部句号、段落边界消失。已改用 `strings.SplitAfter` 并补齐"重建原文/连续子串"性质测试。**注意：已入库的旧 chunks 仍是坏的，必须重新摄入才能生效。**
- **Markdown parser 丢弃代码块**（本阶段修复）：`markdown.go` 的 `walkText` 只提取 `ast.Text` 节点，fenced code block 内容整体丢失（探针测试证实），标题 `#` 层级标记也被抹平。IT 文档中的命令、配置片段从未进入向量库。

在检索质量修复完成前进入阶段 3（ReAct Agent）会放大问题：Agent 的核心工具就是 `kb_retrieval`，检索不准会导致无法区分 Agent 推理错误与检索错误。

## 1. 目标与决策

**目标**：用一套可重复运行的评测工具量化检索质量，按"修复 → 重摄入 → 重跑评测"循环推进，以"基线 → 终态"指标对比作为验收。

**已定决策**（brainstorming 确认）：

| 决策点 | 结论 |
|---|---|
| 范围上限 | **先测量后决策**：不引入混合检索（BM25/RRF）、Reranker、查询改写；评测不达标时数据作为下一阶段立项输入 |
| 评测集来源 | 用户提供 10~20 个真实业务问题 + 期望命中的文档/关键词 |
| 流式取消欠账 | 折入本阶段（CLAUDE.md §2 记录的进阶段 3 前置任务） |
| 切片器 | 不重写 recursive char splitter；结构感知通过摄入管线前置 `sectionize` 步骤实现 |

**非目标**：BM25/Elasticsearch、RRF、Reranker、HyDE/查询改写、多 KB 检索、字符级偏移高亮（均维持 V1.5/V2 推迟状态）。

## 2. 检索评测工具

新增 `backend/cmd/evalretrieval` CLI。

### 2.1 评测集格式

`docs/eval/retrieval-eval.yaml`，用户提供真实问题：

```yaml
- id: q001
  question: "生产环境如何配置数据库连接？"
  expected_document: "部署指南"        # 文档标题（精确匹配）
  expected_keywords: ["DATABASE_URL"]  # 正确切片应包含的关键词（任一命中即算段落级命中）
```

### 2.2 指标

- **文档级 Hit@1 / Hit@3 / Hit@5**：top-k 内出现期望文档；
- **段落级 Hit@5**：top-5 内存在"属于期望文档且内容包含任一期望关键词"的切片；
- **MRR**：按文档级首次命中位置计算。

### 2.3 运行方式

```bash
cd backend
go run ./cmd/evalretrieval -kb <kb_id> -file ../docs/eval/retrieval-eval.yaml
```

- 直连数据库与 embedding API，**复用现有 `service.Retrieval`**，保证评测链路与线上一致；
- 结果打印表格，并落带时间戳的 JSON 到 `docs/eval/results/`，用于纵向对比；
- **第一次运行必须在任何修复重摄入之前**，把当前坏状态记为基线。

## 3. Markdown Parser 修复

重写 `markdown.go` 的文本渲染逻辑，输出保留结构的纯文本：

- 标题保留 `#`/`##`… 层级标记；
- fenced code block / indented code block 用 ``` 围栏保留全部内容；
- 列表、表格保持可读纯文本；
- 段落间维持 `\n\n` 边界。

纯 bug 修复，按 TDD 走（先写"代码块内容必须出现在解析结果中"的失败测试）。

## 4. 结构感知切片（标题路径前缀）

摄入管线新增前置步骤，不改 `ports.Splitter` 接口：

1. 新增 `sectionize`：把 §3 输出的带标记文本按标题切成 `[]Section{Path, Body}`，`Path` 形如 `部署指南 > 环境变量`；
2. worker 对每个 Section 调用现有 splitter；
3. 每个 chunk 内容前拼接标题路径前缀（**计入 token 预算**），path 同时写入 `chunks.metadata`（JSONB map，**无需迁移**）；
4. 超长代码块作为整体交给 splitter，允许硬切，但不与正文段落混在同一 chunk；
5. 非 Markdown 文档（PDF/DOCX/XLSX）无结构信息，退化为现状行为。

## 5. 重新摄入能力

- 新增 sqlc 查询 `DeleteChunksByDocument`（当前不存在删 chunk 查询）；
- `POST /api/kbs/{kbId}/documents/{docId}/reingest`：文档状态置回 `queued`，投递现有 IngestionJob；worker 写入新 chunks 前先删旧 chunks；
- 失败语义：re-ingest 失败时文档为 `failed` 且旧 chunks 已删，用户可再次触发——MVP 可接受；
- `POST /api/kbs/{kbId}/reingest`：全库逐文档投递，调参后一键重建；
- 前端文档列表加"重新处理"按钮（阶段 4 该项提前，因 2.5 反复需要）。

## 6. 中文调参

| 参数 | 现值 | 调整 |
|---|---|---|
| `CHUNK_SIZE` | 800 | 默认改 **400**（env 可调） |
| `CHUNK_OVERLAP` | 120 | 默认改 **60** |
| `RAG_MIN_SCORE` | 0.0（弱证据判断从未生效） | 用评测集校准：对比正确/错误命中的分数分布后定值 |
| `RAG_TOP_K` | 8 | 维持，评测数据说话 |

## 7. 引用展示收敛

- `citation-drawer.tsx` 邻居窗口 2 → 1（展示 3 个 chunk 而非 5 个）；
- 配合 chunk 减半，引用抽屉信息量约为现状 30%，主 chunk 高亮聚焦；
- 不做字符级偏移高亮（V1.5）。

## 8. 流式取消硬化验证

- 后端：SSE handler 自动化测试——客户端断连（ctx cancel）后 LLM 流被取消、不再写入、不落半截 assistant 消息；
- 前端：确认停止按钮/组件卸载走 `AbortController`，中断后 UI 状态正确；
- 手工端到端验证一次并记录结果。

## 9. 实施顺序

```
§2 评测工具 + 跑基线
  → §3 parser 修复
  → §4 结构感知切片
  → §5 重摄入能力 → 全库重建 → 重跑评测
  → §6 调参迭代（每轮重建 + 评测）
  → §7 引用展示收敛
  → §8 流式取消验证
  → 终态评测 + 指标对比
```

## 10. 验收标准

1. 评测集上文档级 **Hit@5 ≥ 80%**；段落级 Hit@5 相比基线显著提升（基线出来后定具体数字并回填本节）；
2. 含代码块答案的问题（如"用什么命令跑迁移"）能检索到代码块内容；
3. `go test ./...`、`pnpm typecheck`、`pnpm test` 全部通过；
4. 流式取消验证通过；
5. 若指标不达标：产出一页数据分析（失败问题分类、分数分布），作为混合检索（V1.5 提前）立项输入。

### 10.1 验收结果（2026-07-08 回填）

| 指标 | 基线（2026-07-07） | 终态（tune-400-60-probes10） |
|---|---|---|
| docHit@1 | 0.92 | **1.00** |
| docHit@5 | 1.00 | **1.00**（达标 ≥ 0.80） |
| passageHit@5 | 1.00 | **1.00**（基线已满分，维持） |
| MRR | 0.942 | **1.000** |

- 代码块用例 code-1/2/3 全部 docRank=1 且 passageHit=true（基线 code-2 docRank=4）；
- 流式取消：SSE 中途断连后无半截 assistant 消息落库、无 done 事件、后端无 panic（单测 + HTTP 端到端均验证）；
- `RAG_MIN_SCORE` 校准为 **0.5**：终态 13/13 正确命中，正确 top_score 最低 0.561；修复前错误命中 top_score 最高 0.42，取中间值；
- **实施中实锤并修复的两个计划外 bug**（详见 eval results 与提交记录）：
  1. 浏览器把 .md 上传为 `application/octet-stream`，Markdown parser 与结构感知切片从未生效 → worker 按文件扩展名推断 MIME（`fix(worker): infer markdown mime`）；
  2. `idx_chunks_ivfflat`（lists=100）在空表上建索引且数据量仅数百行，默认 probes=1 召回塌到 0（q001/code-1 零命中）→ Search 事务内 `SET LOCAL ivfflat.probes = 10`（`fix(vectorstore): raise ivfflat.probes`）。主设计 spec §4.3 "IVFFlat 数据量小够用"的假设不成立，向量量增长后建议重估 HNSW。

## 11. 风险

| 风险 | 缓解 |
|---|---|
| chunk_size 减半导致 chunks 数量翻倍、检索延迟上升 | 单机 MVP 数据量小；评测 CLI 顺带记录检索耗时 |
| 标题前缀污染 embedding（前缀占比过高） | 前缀计入 token 预算；评测对比加前缀前后的指标 |
| 评测集太小（10~20 题）导致指标波动 | 指标只用于方向判断，不做统计显著性结论；失败用例逐条人工分析 |
| re-ingest 失败留下无 chunks 的文档 | 状态可见（failed）+ 可重新触发；不做事务包裹（MVP） |
